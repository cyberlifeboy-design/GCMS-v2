## How sessions work now
- The `RefreshToken` row **is** the session. Its id is carried in the access token as `sid`.
  `authenticate` loads the session on every request and rejects the request if the
  session is missing, past its idle deadline, or past its absolute lifetime.
- The refresh token is an opaque 256-bit random value (it used to be a JWT). Its
  validity lives only in the DB row. Calling `/auth/refresh` does not count as activity.
- Activity moves the idle deadline forward (at most one DB write per minute, per session).
- Access tokens issued before this release have no `sid` and are rejected, so **every user
  has to sign in once after the deploy**.
- No schema change. This uses the existing `RefreshToken.expiresAt` and `createdAt` columns.

## Additional issues found in the full code audit (fixed)
- **Privilege escalation:** an Admin could create **SuperAdmin** accounts through
  `POST /users/bulk` (it had no role check) and through the unused
  `POST /auth/register` (Admin-only, accepted any role). Bulk create now applies the same
  rule as single create (FA only, at the Admin's own venue), and `/auth/register` was
  removed.
- An Admin editing an FA could move that FA to another venue or widen their access
  (`stadiumId`, `assignAllStadiums`, `grantedPages`, `venueReportAccess`). Those fields are
  now ignored for Admin.
- Two sign-ins in the same second could produce the same refresh token. This was fixed by
  switching to random tokens.
- On the account-request page, the department pre-filled from an invitation was wiped out
  as soon as the venue loaded.
- Dependencies: `npm audit fix` on both apps. `xlsx` (prototype pollution / ReDoS, used by
  the fleet bulk import) moved to SheetJS's patched 0.20.3 from cdn.sheetjs.com. `bcrypt`
  went from 5 to 6, which removes the critical `tar` advisory. Tiptap went to 3.31.4 (XSS
  via `mergeAttributes`). There are now **no critical findings** in production
  dependencies for either app.

## Accepted / residual (not exploitable here, or build-time only)
- `nodemailer` (high): the advisory needs the message-level `raw` option, which GCMS never
  uses. The fix is only in v10, whose new package layout breaks the build. Revisit when
  `@types/nodemailer` catches up.
- `image-size` via `pptxgenjs` (high): it only parses images that GCMS generates itself.
  No upstream fix.
- Frontend `tailwindcss` chain (`braces`/`micromatch`): build-time only, never shipped.
- Tokens are still kept in `localStorage`. Moving to httpOnly cookies is a larger change.
  With CSP + 15-minute tokens + server-side session revocation, the impact of XSS token
  theft is now bounded.

## Verification
- Backend: `tsc` clean, **109/109** vitest tests pass. The new test
  `src/middleware/session.test.ts` covers #3, #4 and #5, and `booking-access.test.ts`
  covers #1 and #2.
- Frontend: `tsc` clean, `vite build` OK.
- Local Docker stack against real MySQL: anonymous lookups get 401, forged invite or ID
  token gets 401, and a signed-in user gets 200. Session A is killed by sign-in B (and A's
  refresh token is refused). The idle window is 15.0 min. A background poll does not move
  the deadline, while a real request does. Once the idle deadline passes, the API returns
  `401 SESSION_EXPIRED` and deletes the row.
- Browser: a kicked-out tab is redirected to `/login?reason=session` and the message is
  shown. The account-request page still renders without a sign-in.

## Deploy
Deploy as usual: two image rebuilds and two restarts, with **no `prisma db push`**. See the
runbook's 2026-10-06 addendum. Optional app settings: `SESSION_IDLE_MINUTES` (default 15)
and `SESSION_MAX_HOURS` (default 8).
